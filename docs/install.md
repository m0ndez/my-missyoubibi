# Install

This guide sets up the **Home deployment**: everything runs on one computer at home. To run the page and the broker on a VPS instead, and keep only
the bridge at home, see [Cloud deployment](#cloud-deployment) at the end.

## What you need

- A computer that stays on at home: a Raspberry Pi 4/5, a mini PC or a NAS (Linux, amd64 or arm64) is the intended home. A
  Mac or a Windows PC works for trying it out (see [Platforms](#platforms)).
- **Docker** (with the Compose plugin) or **Podman** with `podman compose`.
- **Node.js 24 or newer** and **git**, only to run `npm run setup`. (Setup is a small script; it doesn't need `npm install`.)
- One or more Mitsubishi Heavy air conditioners with a **WF-RAC Wi-Fi adapter**, already working in the Smart M-Air app, on a
  **2.4 GHz** Wi-Fi network that your computer can reach. See [supported models](supported-models.md).

## Install

```bash
git clone https://github.com/m0ndez/my-missyoubibi
cd my-missyoubibi
npm run setup
```

Setup does four things, and is safe to run again:

1. Detects the network this computer is on (the bridge scans it for your adapters).
2. Writes `.env` with generated secrets (mode 600). A weak or default `APP_PASSWORD` is replaced with a strong one; values you
   chose are kept.
3. Detects your timezone into `TZ` (timers and daily energy totals use it).
4. Builds and starts the stack with Docker, or Podman if Docker isn't installed.

It prints the address (http://localhost:3000) and where to find the password (`APP_PASSWORD` in `.env`). Sign in, then add your
first unit: [add a unit](add-a-unit.md).

Options: `npm run setup -- --pull` fetches the published images instead of building them (falls back to building if they
can't be pulled), `--no-start` only writes `.env`, `--backend` starts only the broker and the bridge (for development).

## What runs

Three containers, started by `docker-compose.yml`:

| Service | What it is |
|---|---|
| `mosquitto` | The message broker. Users and passwords come from `.env`; `mosquitto/acl` limits what each may do. |
| `bridge` | Talks to the adapters. Finds them by MAC, pairs, polls every 5 s and sends changes. |
| `app` | The web page and API, the timer scheduler and the energy recorder. |

All three have healthchecks (`docker compose ps` shows `healthy`). More in [architecture](architecture.md).

## Use it from your phone

`npm run setup` asks whether to serve the page on your Wi-Fi, and prints the address to open on your phone
(`http://<this computer's IP>:3000`, then Share → Add to Home Screen). Say no, or set nothing, and it listens on `127.0.0.1` only. Change your mind:
`npm run setup -- --lan` or `-- --local`. Give this computer a fixed address in your router, or the phone's bookmark breaks when DHCP moves it.
Two ways to reach it from other devices:

- **Recommended: HTTPS with Tailscale.** Install Tailscale on the host and on your phone, then `tailscale serve --bg 3000` and
  open the `https://<name>.ts.net` address it prints. Works away from home too. A reverse proxy with a certificate (Caddy, nginx)
  does the same job.
- **LAN only:** `APP_BIND=0.0.0.0` (what the setup question writes). The password and the session cookie then cross your
  Wi-Fi in clear text; anyone on it can read them.

The page answers only to its own addresses: `localhost`, private and Tailscale IPs, names ending `.local`, `.lan`, `.home.arpa` or
`.ts.net`, and single-word names. Behind a domain of your own (a reverse proxy), list it in `ALLOWED_HOSTS` (a request for any other
name gets `421 Unknown host`).

In the Home deployment, never port-forward port 3000 or 1883 on your router. Signing out (button in the page header) signs out every device; sessions
last 14 days.

## Home Assistant

*Experimental, untested on a real Home Assistant yet.*

Set `HA_DISCOVERY=1` in `.env` (then `npm run setup`) and the app publishes MQTT discovery messages, so each unit shows up as a
climate entity (republished whenever Home Assistant restarts). Home Assistant's MQTT integration must reach the broker:

- Same machine, other container: attach it to this compose network and use host `mosquitto`, port 1883.
- Another machine: set `MQTT_BIND=0.0.0.0` and `MQTT_ALLOW_LAN=1` in `.env` (setup refuses the first without the second). **The broker is not encrypted**: the passwords cross your LAN in clear text,
  so only do this on a network you trust.
- Log in as user `app` with the password `MQTT_PASS` from `.env`. The broker's rules let that user publish commands, read the
  units' state and use `homeassistant/#`.

## Settings

Set these in `.env` (the file `npm run setup` writes), then run `npm run setup` again to apply them.

| Variable | Meaning |
|---|---|
| `APP_PASSWORD`, `AUTH_SECRET` | The login password (10+ characters, no spaces or `$ # " ' \`), and the key that signs session cookies. Generated by setup. |
| `MQTT_PASS`, `MQTT_DEVICE_PASS` | Broker passwords of the `app` and `device` (bridge) users. Generated by setup. |
| `TZ` | Timezone for timers and daily energy totals (detected by setup). |
| `WFRAC_SUBNET` | The LAN the bridge scans for adapters, e.g. `192.168.1.0/24`. Detected by setup; edit it if setup picked the wrong network (a VPN, say). Several, comma separated. |
| `WFRAC_DEVICES` | Optional fixed addresses, `id=ip,...`, instead of finding units by MAC. |
| `WFRAC_REPIN=1` | Accept a new TLS certificate from an HTTPS adapter you replaced. Counts for the first 10 minutes after the bridge starts; remove it afterwards. |
| `APP_BIND` | Where the page listens: `127.0.0.1` (this computer) or `0.0.0.0` (phones on your Wi-Fi). Setup asks once. |
| `ALLOWED_HOSTS` | Extra names the page may be served under, comma separated, `*.example.com` allowed. |
| `MQTT_BIND`, `MQTT_ALLOW_LAN=1` | Where the broker listens (default `127.0.0.1`). Anything else needs `MQTT_ALLOW_LAN=1`: the broker is not encrypted. |
| `WFRAC_CRC=0` | Accept adapter replies whose checksum fails. Only if a model's replies are all refused (`unusable reply` in the bridge log); please report that model. |
| `HA_DISCOVERY=1` | Publish Home Assistant discovery messages. |
| `ENERGY_RATE`, `ENERGY_CURRENCY` | Price per kWh and its symbol, for the cost estimate in the Energy report. |
| `VERSION` | Image tag for `--pull` installs (default `latest`). |

Settings only reach the containers if `docker-compose.yml` lists them: if you add a new one yourself, add it there too.

## Update

- Installed from source (the default): `git pull`, then `npm run setup`. Data is kept.
- Using published images: `npm run setup -- --pull` (or `docker compose pull && docker compose up -d`). The GitHub packages
  must be public for an anonymous pull; if you get `denied`, build from source instead.

Read the [changelog](../CHANGELOG.md) first. Roll back by checking out the previous tag and running setup again.

## Back up and restore

Everything the app keeps is in Docker volumes (the project name is the folder name, shown here as `my-missyoubibi`; list yours with
`docker volume ls`):

| Volume | Holds |
|---|---|
| `app-data` | `devices.json` (your units and their names), `timers.json`, `energy.json` (daily kWh: **the units keep no history, so it can't be rebuilt**), the sign-out marker |
| `bridge-data` | the bridge's identity on your adapters (`wfrac-operator-id`), certificate pins, last-known addresses |
| `mosquitto-data` | retained messages (rebuilt by the bridge; no need to back up) |

```bash
# back up
docker run --rm -v my-missyoubibi_app-data:/d -v "$PWD":/b alpine tar czf /b/app-data.tgz -C /d .
docker run --rm -v my-missyoubibi_bridge-data:/d -v "$PWD":/b alpine tar czf /b/bridge-data.tgz -C /d .

# restore (stack stopped: docker compose down)
docker run --rm -v my-missyoubibi_app-data:/d -v "$PWD":/b alpine sh -c 'tar xzf /b/app-data.tgz -C /d && chown -R 1000:1000 /d'
```

Keep `bridge-data`: the operator id is how the adapters know the bridge. If it is lost the bridge registers as a new app, and each
adapter remembers only 4.

## Uninstall

1. In the page, remove each unit (**Unit settings → Remove unit**). This frees the bridge's slot on the adapter.
2. `docker compose down` stops everything and keeps your data. `docker compose down -v` also **deletes the volumes**, including
   the energy history. Back up first if you might come back.
3. Delete the folder.

Your adapters and the Smart M-Air app are not changed by any of this.

## Platforms

- **Linux (Raspberry Pi OS, Debian, Ubuntu; amd64 and arm64):** the intended platform. CI builds both architectures and starts the
  whole stack. Containers reach the LAN through Docker's normal outbound networking; no special network mode.
- **macOS (Docker Desktop, Podman):** works; it is where this was developed. macOS asks permission before programs may talk to
  devices on your network: see [troubleshooting](troubleshooting.md#every-unit-is-offline-on-a-mac).
- **Windows (Docker Desktop):** best effort and untested. Run `npm run setup` from a normal terminal (not inside a container);
  if the detected network is wrong (virtual adapters), set `WFRAC_SUBNET` in `.env` by hand.
- Containers can't use mDNS (`<mac>.local`) from inside Docker's network, so the bridge scans the subnet instead (it finds each adapter
  by its MAC, so changing addresses are fine).

## Cloud deployment

An optional alternative to everything above, for control from anywhere without Tailscale on each phone: the App and the Broker run on a VPS and
only the Bridge stays at home, connecting outward. It uses the same images and the same code. The full guide is
[cloud-deployment.md](cloud-deployment.md); the steps, in order:

1. [Prepare the VPS](cloud-deployment.md#1-prepare-the-vps): settings, secrets and the firewall (inbound 8883 and SSH only).
2. [The Broker's hostname and certificate](cloud-deployment.md#2-broker-hostname-and-certificate).
3. [Publish the App through a tunnel, behind Cloudflare Access](cloud-deployment.md#3-publish-the-app-tunnel-and-access).
4. [Run the Bridge at home](cloud-deployment.md#4-run-the-bridge-at-home) with `docker-compose.bridge.yml`.
5. [Move your data over](cloud-deployment.md#5-move-your-data-from-the-home-deployment-once) from the Home deployment, once.
6. [Nightly backup to R2, and restore](cloud-deployment.md#6-nightly-backup-to-r2-and-restore).

Before you rely on it, read its [security model](cloud-deployment.md#security-model).
